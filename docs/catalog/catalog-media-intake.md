# Catalog media intake

Status: Phase 18 architect correction implemented at source level; deep validation remains deferred to Phase 26.5.

## Mandatory pre-change repository audit

This audit was completed before changing the Phase 18 media implementation.

| Area | Existing repository mechanism | Phase 18 correction decision |
| --- | --- | --- |
| Upload routes | No application or signed-upload route exists. Profile APIs accept text fields only. Proof-of-delivery accepts a bounded opaque future evidence reference, not bytes or URLs. | Add catalog-only upload-intent, bounded byte-intake and completion routes. |
| Storage adapters | No file/object storage adapter, provider registry, bucket configuration or canonical storage service exists. | Add one provider-neutral catalog adapter boundary. Do not select a cloud provider. |
| Local file storage | No runtime code writes uploaded files to the repository or `public/`. Node filesystem reads are limited to scripts/tests and configuration. | Do not add production local-disk storage. The deterministic adapter is injected directly by tests and is never registered by production code. |
| Object-storage clients | No S3, R2, GCS, Azure Blob or equivalent SDK/configuration exists. | Install no SDK. Production upload creation fails closed until a reviewed adapter is configured in source. |
| Signed-upload/read utilities | None. Payment signatures are provider authentication and are unrelated to storage. | Adapter targets use opaque application references and never reveal credentials or provider secrets. |
| Media serving | Next.js serves repository-owned files under `public/images`; marketing components use `next/image`. There is no database-backed media delivery route. | Add an application delivery boundary that authorizes by asset reference, never storage key. Public delivery remains locked and requires publication evidence. |
| MIME validation | No media MIME/magic-byte validator exists. Import routes validate CSV metadata only. | Add explicit JPEG, PNG and WebP signature inspection and declared/detected MIME agreement. SVG, PDF, GIF, HTML and unrecognized binaries remain prohibited. |
| Checksums | SHA-256 helpers exist for financial/idempotency evidence, but no media-byte checksum service exists. | Compute SHA-256 over server-opened bytes and keep it immutable and private. |
| Dimension readers | No canonical image-dimension reader exists. `sharp` is present only as an optional transitive dependency of Next.js and is not an established application dependency. | Use a narrow, dependency-free JPEG/PNG/WebP header inspector with pixel/decompression limits. Do not claim transformation support. |
| Transformations | No resize, rendition, thumbnail, metadata-strip or catalog transformation pipeline exists. | Store no public originals in Phase 18. Reject supported files containing EXIF/XMP/text metadata instead of silently preserving it. |
| Virus/content scanning | No malware scanner, content-safety service or scanning hook exists. | Represent validation/quarantine evidence and fail uncertain content closed. A reviewed malware/content scanner remains a Phase 26.5 production dependency. |
| Ownership models | Legacy `ProductImage` has an arbitrary URL and no owner. `CatalogMediaAsset` has optional `ownerStoreId` but no explicit platform/store scope. Category, brand, option and product records can reference catalog assets. | Add explicit `PLATFORM`/`STORE` ownership, immutable owner evidence, and database/application cross-owner attachment guards. |
| Public asset URLs | `public/images` contains repository-owned marketing artwork. Legacy category/product image URL fields exist but have no Phase 18 writer. | Do not ingest or reuse arbitrary remote URLs. Catalog DTOs expose only public asset references and controlled application routes. |
| Test adapters | Payment tests have their own provider fakes, but no storage/media adapter exists. | Add a deterministic in-memory catalog storage adapter available only by direct dependency injection. |

The audit confirms that there is no competing canonical storage architecture. The catalog adapter introduced here is intentionally narrow and cannot be reused implicitly for proof-of-delivery or unrelated documents.

## Final boundary

`CatalogMediaStorageAdapter` owns provider-facing upload targets, byte confirmation, validation reads, uncommitted cleanup and controlled reads. Storage keys are opaque and generated by the server. The production registry has no active adapter while `CATALOG_MEDIA_PRODUCTION_VALIDATION_APPROVED` is false; direct tests inject the deterministic adapter without an environment bypass.

The application owns authentication, exact permissions, tenant ownership, intent idempotency, lifecycle transitions, content inspection, checksum calculation, attachment policy, audit history and safe DTO construction. Storage providers never decide catalog authorization.

## Lifecycle

Assets move through `PENDING_UPLOAD`, `UPLOADED`, `VALIDATING`, `READY`, `QUARANTINED`, `REJECTED` and `ARCHIVED`. Only `READY` assets may be associated. Upload intents move through `PENDING_UPLOAD`, `UPLOADED`, `COMPLETED`, `EXPIRED` or `CANCELLED`; they cannot complete twice or after expiry.

## Current production limitation

No cloud provider, malware scanner or public rendition service has been selected. Production upload creation and public delivery therefore fail with `CONSOLIDATED_VALIDATION_NOT_APPROVED`. Metadata-bearing images are rejected rather than transformed, so EXIF GPS and device-owner metadata are not exposed. Provider configuration, scanner behavior, transformed renditions and live browser delivery require Phase 26.5 validation.
