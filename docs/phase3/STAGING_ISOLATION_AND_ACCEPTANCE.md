# Staging isolation and acceptance

STAGING_BLOCKED. No cloud staging resources created, no cost committed, no production credentials copied. A pending owner request asks for approving owner, plan, currency/maximum spend and disposal date. No response is interpreted as approval.

`npm run staging:preflight -- <operator-reviewed-resource-policy.json>` reads explicit environment variables without dotenv, network, provider or database calls. Current supported mode is offline only: console communications, Paystack/PayFast disabled, payout disabled, local disposable media/artifacts. It rejects unknown URL endpoints, live key prefixes, shared secrets by fingerprint, protected production IDs/hosts, production-marked database/buckets, unreviewed worker commands, shared cookie domain and mismatched resource identity/Redis queue namespace. Every configured credential requires an approved fingerprint. The protected inventory must come from the infrastructure owner's separately approved audit, never autonomously fetched secret values.

The JSON policy must contain named dated authority with evidenceRef/currency/maxSpend/expiry, protectedInventoryRef and protected fingerprints/resource IDs, exact Railway staging project/environment, allowed hosts/database/Redis DB/queue namespace/storage resources/worker commands and expected secret fingerprints. Synthetic test fixtures are clearly labelled and authorize nothing. Do not copy fixture names into a real approval. Sandbox egress/provider integration is deliberately not allowed by this initial guard; its reviewed adapter/egress policy is a further engineering task before provider staging acceptance.

The preflight guard is preparation, not proof that infrastructure networking enforces isolation. Before registering an edge origin in source: create approved separate Vercel/Railway projects, independent Postgres/Redis/storage, pass guard with independently reviewed fingerprints, enforce egress, migrate synthetic data, restore test, verify worker leasing/health, then test exact-source role journeys and edge routes. Confirm deployment metadata, aliases, host-only cookies and no production webhook/queue targets. Capture actual monitoring and cleanup receipts. Only then may an operator sign STAGING_ACCEPTED.
