# Marketplace and order acceptance

The five-product exemplar covers one store and five cart lines. Existing directed and canonical PostgreSQL cases remain necessary for multi-store legs, substitution consent, cancellation, refund and source-bound payment invariants. No redirect alone establishes payment success. Canonical payment/order binding, independently reviewed immutable publication/price snapshots and inventory reservations remain the state authority.

Trusted single prepackaged classification is preserved. Ambiguous aggregates remain UNKNOWN/blocked unless a reviewed ANY tariff permits them; the exemplar's synthetic policy does not invent a live multi-parcel aggregation formula. Parcel dimensions, weight bands, aggregation, coverage polygons, effective tariffs, tax, rounding and operating hours need explicit operator input before activation. Stale reviewed package/offer/modifier versions must invalidate the selection.

Real Paystack, merchant bank reconciliation, settlement and refund acceptance were not performed. Signed webhook and server-side verification remain mandatory; see [Paystack webhook documentation](https://paystack.com/docs/payments/webhooks/) and [verification documentation](https://paystack.com/docs/payments/verify-payments/).

Seller identity proposals become versioned approved authority only through independent review and durable owner/review audit. Existing and frozen legal facts are preserved; stale parents, reused versions and overlapping legacy windows refuse. These actions do not post money or activate commercial rules.
